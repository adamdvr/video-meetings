# Plan: Профиль пользователя и его редактирование

**PRD:** [docs/prd-user-profile.md](prd-user-profile.md)

**Дата:** 2026-11-11, задачи переразбиты на вертикальные срезы 2026-11-16

## Фазы реализации

Фазы идут по порядку. Каждая опирается на api или страницу из предыдущих и оставляет приложение рабочим, поэтому остановиться можно после любой. Три пары фаз (api → web) независимы по смыслу: имя, аватар, пароль. Пару «пароль» (фазы 5–6) можно делать сразу после фазы 2, не дожидаясь аватара.

Каждая задача — вертикальный срез: одно наблюдаемое поведение со своими тестами, кодом и документацией. Из задачи получается Issue, которую Ralph loop решает за одну сессию, и сессия заканчивается зелёным коммитом. TDD идёт внутри задачи: в api тесты пишутся на Vitest и supertest (`apps/api/test`), в web на Playwright Test (`apps/web/e2e`).

1. Написать тесты задачи до кода.
2. Запустить их и убедиться, что они красные по нужной причине. Ожидаемый отказ (400, 401, 404) проверяется вместе с позитивным сценарием, иначе тест «пройдёт» на 404 от ещё не существующего роута.
3. Реализовать поведение, пока тесты не станут зелёными, прогнать все проверки приложения и закоммитить код с тестами, затем документацию.

Красные тесты и хуки. Stop-хук прогоняет `test:e2e` api в конце хода и блокирует его, пока тесты красные; web-тесты он не запускает, но `check-types` и `lint` по ним должны проходить. pre-commit не пропускает красные тесты. Поэтому красное состояние существует только внутри задачи, а отдельных задач «сначала тесты» в плане нет: такая задача не может закончиться зелёной. Слои без наблюдаемого поведения (поле в модели, сообщения модуля) входят в первую задачу, которой они нужны.

Вручную остаётся проверка UI из `apps/web/CLAUDE.md` (375 px, тёмная тема, клавиатура, axe-core) и перезапуск api для проверки, что аватар сохраняется.

Разделение по модулям api. Имя и аватар — данные пользователя: эндпоинты `/users/me…` в модуле `users` (у него появляется контроллер под `JwtAuthGuard`, который работает без импорта `auth`). Смена пароля проверяет и хеширует пароль и выдаёт токен, поэтому это `POST /auth/password` в модуле `auth`, который ходит в `users` только через шину, как регистрация и вход.

## Фаза 1: Профиль и имя в api

**Цель:** минимальный путь профиля через api (tracer bullet): получить свой профиль и изменить имя.

**Затрагивает:** backend, database

**Задачи:**

- [ ] **`GET /users/me` отдаёт свой профиль.** Тесты: новый пользователь получает `id`, `email`, `name: null`, `createdAt`, `avatarUpdatedAt: null` и ровно эти поля, без `passwordHash`; без токена и с неверным токеном — 401. Код: необязательное поле `name` в модели `User` и миграция; `UserView` и `toUserView` дополнены; запрос профиля по `id` в модуле `users`; контроллер `users` под `JwtAuthGuard` с `GET /users/me` и ответом `ProfileView` (`avatarUpdatedAt` до фазы 3 всегда `null`). Документация: `apps/api/CLAUDE.md` (контроллер и запрос `users`, эндпоинт, `ProfileView`).
- [ ] **`PATCH /users/me` меняет имя.** Тесты: имя возвращается обрезанным по краям и приходит в следующем `GET`; имя ровно из 100 символов принимается; `name: null` удаляет имя; строка из пробелов и имя длиннее 100 символов — 400 с сообщением, начинающимся с `name`, имя не меняется; без токена — 401, имя не меняется; пользователь видит и меняет только себя (имя одного не появляется у другого). Код: DTO (`name`: `null` или строка 1–100 символов после обрезки), команда изменения имени в `users`, эндпоинт `PATCH /users/me` с ответом `ProfileView`. Документация: `apps/api/CLAUDE.md` (эндпоинт, команда, правила имени).

**Когда готова:** e2e-тесты фазы зелёные в `npm run test:e2e -- --force`; `check-types`, `lint`, `build` api зелёные; `curl` с токеном демо-аккаунта меняет и читает имя.

## Фаза 2: Страницы профиля, имя и шапка в web

**Цель:** пользователь открывает профиль из шапки, указывает имя и видит его в шапке на всех страницах.

**Затрагивает:** frontend

**Задачи:**

- [ ] **Страница `/profile` показывает профиль и закрыта без входа.** Тесты: `/profile` показывает кружок с первой буквой email, «Имя не указано», email и дату регистрации; без входа `/profile` и `/profile/edit` ведут на `/login`. Код: `getProfile()` в `src/lib` (вызов `GET /users/me`, тип `Profile` зеркалит `ProfileView` api); страница `/profile` с аватаром-заглушкой (первая буква имени или email), именем или «Имя не указано», email, датой регистрации и кнопкой «Редактировать»; состояния загрузки и ошибки «Не удалось загрузить профиль» с «Повторить»; пути `/profile` и `/profile/edit` в `matcher` proxy и в самой функции: без сессии — `/login`. Документация: `apps/web/CLAUDE.md` (страница профиля, правило proxy).
- [ ] **Шапка ведёт в профиль.** Тесты: на главной и на странице встречи в шапке кружок с буквой и email; клик по нему открывает `/profile`; «Выйти» работает как раньше. Код: `AppHeader` с кружком и именем (или email) в своей `<Suspense>`, ссылка на `/profile`; шапка и список встреч не ждут друг друга. Документация: `apps/web/CLAUDE.md` (шапка).
- [ ] **Имя редактируется на `/profile/edit`.** Тесты: «Редактировать» в профиле ведёт на `/profile/edit`; сохранённое имя видно в шапке на главной, на странице встречи и в профиле; очистка поля возвращает в шапку email, а в профиль «Имя не указано»; имя из пробелов и длиннее 100 символов — ошибка у поля, имя не меняется. Код: страница `/profile/edit`, форма «Профиль» с полем имени; Server Action вызывает `PATCH /users/me` и обновляет страницу; пустое поле удаляет имя; ошибки api по префиксу `name` показаны у поля, проверка на клиенте повторяет правила api. Документация: `apps/web/CLAUDE.md` (страница редактирования, форма).

**Когда готова:** e2e-тесты фазы зелёные в `npm run test:e2e -- --force`; проверка UI из `apps/web/CLAUDE.md` пройдена на `/profile`, `/profile/edit` и шапке; `lint`, `check-types` и `build` web зелёные.

## Фаза 3: Аватар в api

**Цель:** api принимает, хранит, отдаёт и удаляет аватар пользователя.

**Затрагивает:** backend, database

**Задачи:**

- [ ] **Аватар загружается и отдаётся.** Тесты: `PUT /users/me/avatar` с PNG, JPG и WebP → `GET /users/me/avatar` отдаёт те же байты с типом из таблицы форматов и `nosniff`, а `avatarUpdatedAt` в профиле заполнен; повторная загрузка заменяет аватар; пользователь без аватара получает 404, а не чужой; без токена `PUT` и `GET` — 401; путь на диске не попадает в ответы. Код: поле с датой обновления аватара в модели `User` и миграция; таблица форматов (PNG, JPG/JPEG, WebP: расширение, MIME-тип, сигнатура); хранение в `<FILES_DIR>/avatars/<userId>` через временный файл и переименование, чтобы прерванная загрузка не портила текущий аватар; эндпоинты `PUT` и `GET /users/me/avatar` и сообщения модуля `users` для них; `GET` отдаёт файл с `Cache-Control: private, no-cache` и `ETag`. Документация: `apps/api/CLAUDE.md` (эндпоинты, хранение, форматы), README (где лежат аватары).
- [ ] **Неподходящий файл отклоняется, прежний аватар остаётся.** Тесты: пустой файл — 400, больше 5 МБ — 413, другой формат и PNG с расширением `.jpg` (содержимое не совпадает с форматом) — 415; после каждого отказа `GET` отдаёт прежний аватар. Код: проверки в порядке файлов встреч (`Content-Length`, пустой, 5 МБ до чтения тела, формат, сигнатура на лету); отклонённая загрузка удаляет временный файл. Документация: `apps/api/CLAUDE.md` (порядок проверок, коды ответов).
- [ ] **Аватар удаляется.** Тесты: `DELETE /users/me/avatar` удаляет файл с диска, после него `GET` — 404 и `avatarUpdatedAt: null`; без токена — 401. Код: эндпоинт `DELETE /users/me/avatar` и команда модуля `users`. Документация: `apps/api/CLAUDE.md` (эндпоинт удаления).

**Когда готова:** e2e-тесты фазы зелёные в `npm run test:e2e -- --force`; после перезапуска api аватар отдаётся с тем же SHA-256.

## Фаза 4: Аватар в web

**Цель:** пользователь загружает, меняет и удаляет аватар и видит его в шапке и в профиле.

**Затрагивает:** frontend

**Задачи:**

- [ ] **Аватар загружается и показывается.** Тесты: выбранная картинка видна в превью до сохранения, после «Сохранить» аватар показан в шапке на главной, на странице встречи и в профиле; адрес аватара без входа ведёт на `/login`, а под другим пользователем не отдаёт чужую картинку. Код: Route Handlers аватара (вне `matcher` proxy, как файлы встреч): загрузка потоком в `PUT /users/me/avatar` (Server Action ограничен 1 МБ) и показ с проверкой сессии, передачей `ETag` и белым списком заголовков; выбор файла с превью в форме «Профиль»; компонент аватара для шапки и профиля: картинка кругом с обрезкой по центру, адрес с `avatarUpdatedAt`, чтобы после смены не показывался старый из кэша, без аватара — кружок с буквой. Документация: `apps/web/CLAUDE.md` (Route Handlers аватара, компонент).
- [ ] **Неподходящий файл не принимается.** Тесты: файл другого формата, пустой и больше 5 МБ показывают причину отказа у поля, прежний аватар остаётся. Код: проверка формата, пустоты и размера на клиенте (правила повторяют таблицу api); ошибки api показаны у поля. Документация: `apps/web/CLAUDE.md` (правила файла).
- [ ] **Аватар удаляется.** Тесты: «Удалить аватар» возвращает кружок с буквой в шапке и в профиле. Код: кнопка «Удалить аватар» в форме «Профиль» и вызов `DELETE /users/me/avatar`. Документация: `apps/web/CLAUDE.md` (удаление аватара).

**Когда готова:** e2e-тесты фазы зелёные в `npm run test:e2e -- --force`; проверка UI из `apps/web/CLAUDE.md` пройдена; `lint`, `check-types` и `build` web зелёные.

## Фаза 5: Смена пароля и отзыв сессий в api

**Цель:** пользователь меняет пароль по текущему, а токены, выданные до смены, перестают приниматься.

**Затрагивает:** backend, database

**Задачи:**

- [ ] **`POST /auth/password` меняет пароль.** Тесты: верный текущий пароль → новый `accessToken`, который принимается на `GET /users/me`; вход со старым паролем — 401, с новым — 200; неверный текущий пароль, новый пароль вне 8–128 символов и новый, совпадающий с текущим, — 400 с сообщением, начинающимся с имени поля, пароль не меняется (не 401: web считает 401 концом сессии); без токена — 401. Код: команда смены пароля в `auth`: проверяет текущий пароль, хеширует новый, сохраняет хеш через команду модуля `users` и выдаёт новый токен. Документация: `apps/api/CLAUDE.md` (эндпоинт, команды).
- [ ] **Токены, выданные до смены пароля, отклоняются.** Тесты: после смены пароля старый токен на `GET /users/me` и `GET /meetings` — 401, новый — 200; токен без версии в payload (выданный до выкатки) принимается, пока пароль не сменён; токен удалённого пользователя — 401. Код: поле версии пароля в модели `User` и миграция; токен несёт версию в payload, токен без неё считается версией по умолчанию; команда смены пароля сохраняет хеш и увеличивает версию одним обновлением; `JwtAuthGuard` после проверки подписи запрашивает пользователя через шину `users` и отклоняет токен с устаревшей версией или несуществующего пользователя. Документация: `apps/api/CLAUDE.md` (версия в токене, guard ходит в БД, изменение поведения для удалённых пользователей).

**Когда готова:** e2e-тесты фазы зелёные в `npm run test:e2e -- --force`; смоук собранного api (`node apps/api/dist/main.js` на свободном `PORT`): регистрация, вход, смена пароля, старый токен — 401, новый — 200.

## Фаза 6: Смена пароля в web и выход по отозванной сессии

**Цель:** пользователь меняет пароль в форме и остаётся в системе, а отозванная сессия на другом устройстве попадает на страницу входа.

**Затрагивает:** frontend

**Задачи:**

- [ ] **Пароль меняется в форме.** Тесты: верные данные → «Пароль изменён», пользователь остаётся в системе; выход и вход со старым паролем — «Неверный email или пароль», с новым — успешно; неверный текущий пароль — «Неверный пароль» у поля; короткий, длинный, совпадающий с текущим и не совпадающий с повтором новый пароль — ошибка у своего поля, пароль не меняется. Код: форма «Смена пароля» на `/profile/edit`: текущий, новый и повтор (`autoComplete` `current-password` и `new-password`), проверка на клиенте; Server Action вызывает `POST /auth/password` и записывает новый токен в cookie `access_token`. Документация: `apps/web/CLAUDE.md` (форма пароля).
- [ ] **Отозванная сессия ведёт на вход.** Тесты: второй контекст браузера, вошедший до смены пароля, при переходе на главную, страницу встречи и `/profile` попадает на `/login`, а cookie `access_token` удалена. Код: ответ 401 от api на страницах (главная, встреча, профиль, шапка) ведёт на Route Handler выхода, который удаляет cookie и перенаправляет на `/login` (Server Component не может менять cookie). Документация: `apps/web/CLAUDE.md` (обработка 401), README (смена пароля завершает другие сессии).

**Когда готова:** e2e-тесты фазы зелёные в `npm run test:e2e -- --force`; проверка UI из `apps/web/CLAUDE.md` пройдена; `lint`, `check-types` и `build` web зелёные; полная проверка `npx turbo run lint check-types test test:e2e build && npm run format:check` зелёная.
