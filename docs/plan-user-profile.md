# Plan: Профиль пользователя и его редактирование

**PRD:** [docs/prd-user-profile.md](prd-user-profile.md)

**Дата:** 2026-11-11

## Фазы реализации

Фазы идут по порядку. Каждая опирается на api или страницу из предыдущих и оставляет приложение рабочим, поэтому остановиться можно после любой. Три пары фаз (api → web) независимы по смыслу: имя, аватар, пароль. Пару «пароль» (фазы 5–6) можно делать сразу после фазы 2, не дожидаясь аватара.

Каждая фаза начинается с e2e-тестов: в api это Vitest и supertest (`apps/api/test`), в web — Playwright Test (`apps/web/e2e`).

1. Написать тесты на критерии фазы до кода.
2. Запустить их и убедиться, что они красные по нужной причине. Ожидаемый отказ (400, 401, 404) проверяется вместе с позитивным сценарием, иначе тест «пройдёт» на 404 от ещё не существующего роута.
3. Реализовать фазу, пока тесты не станут зелёными, и закончить честным прогоном `npm run test:e2e -- --force`.

Вручную остаётся проверка UI из `apps/web/CLAUDE.md` (375 px, тёмная тема, клавиатура, axe-core) и перезапуск api для проверки, что аватар сохраняется.

Красные тесты и хуки. Stop-хук прогоняет `test:e2e` api в конце хода и блокирует его, пока тесты красные; web-тесты он не запускает, но `check-types` и `lint` по ним должны проходить. Отключить хук на красную фазу (`.claude/hooks/.verify-off`) — решение пользователя. pre-commit не пропускает красные тесты, поэтому они коммитятся вместе с реализацией.

Разделение по модулям api. Имя и аватар — данные пользователя: эндпоинты `/users/me…` в модуле `users` (у него появляется контроллер под `JwtAuthGuard`, который работает без импорта `auth`). Смена пароля проверяет и хеширует пароль и выдаёт токен, поэтому это `POST /auth/password` в модуле `auth`, который ходит в `users` только через шину, как регистрация и вход.

## Фаза 1: Профиль и имя в api

**Цель:** минимальный путь профиля через api (tracer bullet): получить свой профиль и изменить имя.

**Затрагивает:** backend, database

**Задачи:**

- [ ] Сначала e2e-тесты: `GET /users/me` нового пользователя возвращает `id`, `email`, `name: null`, `createdAt`, `avatarUpdatedAt: null` и не содержит `passwordHash`; `PATCH /users/me` с именем → оно возвращается обрезанным по краям и приходит в следующем `GET`; `name: null` удаляет имя; строка из пробелов и имя длиннее 100 символов — 400 с сообщением, начинающимся с `name`; пользователь видит и меняет только себя (имя одного не появляется у другого); без токена — 401.
- [ ] Поле `name` (необязательное) в модели `User` и миграция; `UserView` и `toUserView` дополнены.
- [ ] Сообщения модуля `users`: запрос профиля по `id` и команда изменения имени; контроллер `GET /users/me` и `PATCH /users/me` с DTO (`name`: `null` или строка 1–100 символов после обрезки) и ответом `ProfileView` без хеша пароля.
- [ ] Документация: `apps/api/CLAUDE.md` (контроллер и сообщения `users`, эндпоинты, правила имени).

**Когда готова:** e2e-тесты фазы зелёные в `npm run test:e2e -- --force`; `check-types`, `lint`, `build` api зелёные; `curl` с токеном демо-аккаунта меняет и читает имя.

## Фаза 2: Страницы профиля, имя и шапка в web

**Цель:** пользователь открывает профиль из шапки, указывает имя и видит его в шапке на всех страницах.

**Затрагивает:** frontend

**Задачи:**

- [ ] Сначала e2e-тесты: клик по имени/email в шапке открывает `/profile` с кружком-буквой, «Имя не указано», email и датой регистрации; «Редактировать» ведёт на `/profile/edit`; сохранённое имя видно в шапке на главной, на странице встречи и в профиле; очистка поля возвращает в шапку email; имя из пробелов и длиннее 100 символов — ошибка у поля, имя не меняется; без входа `/profile` и `/profile/edit` ведут на `/login`.
- [ ] `getProfile()` в `src/lib` (вызов `GET /users/me`, тип `Profile` зеркалит `ProfileView` api) и `/profile`: аватар-заглушка с первой буквой имени или email, имя или «Имя не указано», email, дата регистрации, кнопка «Редактировать»; состояния загрузки и ошибки «Не удалось загрузить профиль» с «Повторить».
- [ ] `/profile/edit`, форма «Профиль» с полем имени: Server Action вызывает `PATCH /users/me` и обновляет страницу; пустое поле удаляет имя; ошибки api по префиксу `name` показаны у поля, проверка на клиенте повторяет правила api.
- [ ] Шапка `AppHeader`: кружок с буквой и имя (или email) в своей `<Suspense>`, клик ведёт на `/profile`, «Выйти» на месте; шапка и список встреч не ждут друг друга. Пути `/profile` и `/profile/edit` добавлены в `matcher` proxy и в саму функцию: без сессии — `/login`.
- [ ] Документация: `apps/web/CLAUDE.md` (страницы профиля, шапка, правило proxy).

**Когда готова:** e2e-тесты фазы зелёные в `npm run test:e2e -- --force`; проверка UI из `apps/web/CLAUDE.md` пройдена на `/profile`, `/profile/edit` и шапке; `lint`, `check-types` и `build` web зелёные.

## Фаза 3: Аватар в api

**Цель:** api принимает, хранит, отдаёт и удаляет аватар пользователя.

**Затрагивает:** backend, database

**Задачи:**

- [ ] Сначала e2e-тесты: `PUT /users/me/avatar` с PNG, JPG и WebP → `GET /users/me/avatar` отдаёт те же байты с типом из таблицы форматов и `nosniff`, а `avatarUpdatedAt` в профиле заполнен; повторная загрузка заменяет аватар; пустой файл — 400, больше 5 МБ — 413, другой формат и PNG с расширением `.jpg` (содержимое не совпадает с форматом) — 415, прежний аватар после отказа не меняется; `DELETE /users/me/avatar` удаляет файл с диска, после него `GET` — 404 и `avatarUpdatedAt: null`; пользователь без аватара получает 404, а не чужой; без токена — 401; путь на диске не попадает в ответы.
- [ ] Поле с датой обновления аватара в модели `User` и миграция; хранение в `<FILES_DIR>/avatars/<userId>`: запись во временный файл и переименование, чтобы прерванная или отклонённая загрузка не портила текущий аватар.
- [ ] Таблица форматов аватара (PNG, JPG/JPEG, WebP: расширение, MIME-тип, сигнатура) и проверки в порядке файлов встреч (`Content-Length`, пустой, 5 МБ до чтения тела, формат, сигнатура на лету).
- [ ] Эндпоинты `PUT`, `GET`, `DELETE /users/me/avatar` и сообщения модуля `users` для них; `GET` отдаёт файл с `Cache-Control: private, no-cache` и `ETag`.
- [ ] Документация: `apps/api/CLAUDE.md` (эндпоинты аватара, хранение, форматы), README (где лежат аватары).

**Когда готова:** e2e-тесты фазы зелёные в `npm run test:e2e -- --force`; после перезапуска api аватар отдаётся с тем же SHA-256.

## Фаза 4: Аватар в web

**Цель:** пользователь загружает, меняет и удаляет аватар и видит его в шапке и в профиле.

**Затрагивает:** frontend

**Задачи:**

- [ ] Сначала e2e-тесты: выбранная картинка видна в превью до сохранения, после «Сохранить» аватар показан в шапке на главной, на странице встречи и в профиле; файл другого формата, пустой и больше 5 МБ показывают причину отказа, прежний аватар остаётся; «Удалить аватар» возвращает кружок с буквой; адрес аватара без входа ведёт на `/login`, а под другим пользователем не отдаёт чужую картинку.
- [ ] Route Handlers аватара в web (вне `matcher` proxy, как файлы встреч): загрузка потоком в `PUT /users/me/avatar` (Server Action ограничен 1 МБ) и показ с проверкой сессии, передачей `ETag` и белым списком заголовков.
- [ ] В форме «Профиль» выбор файла с превью и проверкой формата, пустоты и размера на клиенте (правила повторяют таблицу api), «Удалить аватар»; ошибки api показаны у поля.
- [ ] Компонент аватара для шапки и профиля: картинка кругом с обрезкой по центру, адрес с `avatarUpdatedAt`, чтобы после смены не показывался старый из кэша; без аватара — кружок с буквой.
- [ ] Документация: `apps/web/CLAUDE.md` (Route Handlers аватара, компонент, правила файла).

**Когда готова:** e2e-тесты фазы зелёные в `npm run test:e2e -- --force`; проверка UI из `apps/web/CLAUDE.md` пройдена; `lint`, `check-types` и `build` web зелёные.

## Фаза 5: Смена пароля и отзыв сессий в api

**Цель:** пользователь меняет пароль по текущему, а токены, выданные до смены, перестают приниматься.

**Затрагивает:** backend, database

**Задачи:**

- [ ] Сначала e2e-тесты: `POST /auth/password` с верным текущим паролем возвращает новый `accessToken`; вход со старым паролем — 401, с новым — 200; старый токен на `GET /users/me` и `GET /meetings` — 401, новый — 200; неверный текущий пароль, новый пароль вне 8–128 символов и новый, совпадающий с текущим, — 400 с сообщением, начинающимся с имени поля, пароль не меняется (не 401: web считает 401 концом сессии); токен удалённого пользователя — 401; без токена — 401.
- [ ] Поле версии пароля (или даты его смены) в модели `User` и миграция; токен несёт эту версию в payload, токены без неё считаются версией по умолчанию, чтобы уже выданные сессии не оборвались при выкатке.
- [ ] `JwtAuthGuard` после проверки подписи запрашивает пользователя через шину `users` и отклоняет токен с устаревшей версией или несуществующего пользователя.
- [ ] Команда смены пароля в `auth`: проверяет текущий пароль, хеширует новый, через команду модуля `users` сохраняет хеш и увеличивает версию в одном обновлении и выдаёт новый токен.
- [ ] Документация: `apps/api/CLAUDE.md` (эндпоинт, версия в токене, guard ходит в БД, изменение поведения для удалённых пользователей).

**Когда готова:** e2e-тесты фазы зелёные в `npm run test:e2e -- --force`; смоук собранного api (`node apps/api/dist/main.js` на свободном `PORT`): регистрация, вход, смена пароля, старый токен — 401, новый — 200.

## Фаза 6: Смена пароля в web и выход по отозванной сессии

**Цель:** пользователь меняет пароль в форме и остаётся в системе, а отозванная сессия на другом устройстве попадает на страницу входа.

**Затрагивает:** frontend

**Задачи:**

- [ ] Сначала e2e-тесты: верные данные → «Пароль изменён», пользователь остаётся в системе, выход и вход со старым паролем — «Неверный email или пароль», с новым — успешно; второй контекст браузера, вошедший до смены, при переходе на главную, страницу встречи и `/profile` попадает на `/login`; неверный текущий пароль — «Неверный пароль» у поля; короткий, длинный, совпадающий с текущим и не совпадающий с повтором новый пароль — ошибка у своего поля, пароль не меняется.
- [ ] Форма «Смена пароля» на `/profile/edit`: текущий, новый и повтор (`autoComplete` `current-password` и `new-password`), проверка на клиенте; Server Action вызывает `POST /auth/password` и записывает новый токен в cookie `access_token`.
- [ ] Ответ 401 от api на страницах (главная, встреча, профиль, шапка) удаляет cookie и ведёт на `/login`. Server Component не может менять cookie, поэтому это редирект на Route Handler выхода.
- [ ] Документация: `apps/web/CLAUDE.md` (форма пароля, обработка 401), README (смена пароля завершает другие сессии).

**Когда готова:** e2e-тесты фазы зелёные в `npm run test:e2e -- --force`; проверка UI из `apps/web/CLAUDE.md` пройдена; `lint`, `check-types` и `build` web зелёные; полная проверка `npx turbo run lint check-types test test:e2e build && npm run format:check` зелёная.
