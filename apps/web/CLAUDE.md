@AGENTS.md

## apps/web

Frontend on Next.js 16.4 (App Router), React 19.3, Tailwind CSS 4 and TypeScript 5.9. Turbopack is used in both `dev` and `build`. The code lives in `src/app` (routes), `src/components` (shared components), `src/lib` (helpers: api calls, session and meetings for the server, `file-size.ts` and `file-rules.ts` shared with client components), `src/proxy.ts` (redirect before render) and `e2e` (Playwright tests); the `@/*` alias points to `./src/*`. Port 3000.

## Commands

Run as `npm run <script> -w web` from the root or through turbo: `npm run <task> -- --filter=web`.

- `dev`, `build`, `start` — the standard `next` commands.
- `lint` / `lint:fix` — the ESLint CLI. Next 16 has no `next lint` command.
- `check-types` — `next typegen && tsc --noEmit`. `typegen` generates the route types into `.next/types` and `next-env.d.ts`; neither file is committed.
- `test:e2e` — `playwright test`, the e2e tests in `e2e/*.spec.ts` (config `playwright.config.ts`, Playwright Test, Chromium only). Extra arguments go after `--`: `npm run test:e2e -w web -- --ui`, `-- -g "чужая"`.

## E2E tests

- `webServer` in `playwright.config.ts` reuses the dev servers already listening on 3000 (web) and 4000 (api) and otherwise starts `npm run dev` of both apps itself (from the repository root) and stops them afterwards. So the tests run against `next dev`, the database is the dev one, and the api address is `API_URL` (default `http://localhost:4000`). The web address is fixed to `http://localhost:3000`: Next dev does not hydrate pages opened by another host.
- The browser is downloaded once per machine: `npm exec -w web -- playwright install chromium`. Without it every test fails with `Executable doesn't exist`.
- Data is prepared through the api REST, not through the UI: `e2e/api.ts` has `registerUser` (a unique `user-<uuid>@example.com`, as in the api e2e tests), `createMeeting`, `uploadFile` (a `Buffer` straight to `POST /meetings/:id/files`; api accepts only the PRD formats and checks the first bytes, so test files come from `fileBytes(format, size)` in `e2e/file-bytes.ts`, which prepends the signature) and `signIn`, which puts the token into the `access_token` cookie of the browser context. Nothing is deleted afterwards. Logged-out checks use a context without `signIn`.
- After a client-side navigation the previous route stays in the DOM hidden by `<Activity>`: role locators skip it, but CSS locators do not, so scope them with `:visible` (`main:visible time`).
- Dates: the tests set `timezoneId` and compute the expected text with `localDate` from `e2e/dates.ts`, which uses the same `Intl.DateTimeFormat` options as `MeetingDate`: do not hard-code the formatted string, ICU output differs between versions.
- Downloads: `page.waitForEvent('download')`, then `suggestedFilename()` and the SHA-256 of `download.path()`. Statuses of the download Route Handler are checked with `context.request`, which shares the browser context's cookies.
- Uploads (`e2e/meeting-file-upload.spec.ts`): files are written to `testInfo.outputPath()` and picked through `page.waitForEvent('filechooser')` after a click on "Выбрать файлы" (passing a path, not a buffer: `setInputFiles` with a buffer is limited to 50 MiB). Drag and drop goes through CDP `Input.dispatchDragEvent` (`dragEnter`, `dragOver`, `drop` with `data.files` as paths): a synthetic `DataTransfer` built in the page does not work, because react-aria reads files through `webkitGetAsEntry()`, which is `null` for such a `File`, and drops them silently. Progress is visible only on a slowed upload: CDP `Network.emulateNetworkConditions` with `uploadThroughput`. A failure of one file is simulated with `page.route` on `**/meetings/<id>/files` that answers 500 by the `X-File-Name` header. "No reload" is proven by a marker put on `window` before the upload and still present after it. Shared helpers (`chooseFiles`, `fileRows`, `uploadRow`, `slowDownUploads`, `uploadProgress`) live in `e2e/upload.ts`.
- Failures (`e2e/meeting-file-upload-failures.spec.ts`): a file over 1 GiB is sparse (`FileHandle.truncate`, nothing is written to disk); "no request was sent" is proven by recording the `X-File-Name` of POSTs with `page.on('request')`. Cancel runs on a slowed upload, and `listFiles` from `e2e/api.ts` checks the meeting on api. A connection drop is `route.abort('internetdisconnected')` on the first attempt: CDP `offline: true` does not break an upload already in flight, the file kept going and was saved. The real mid-body abort through the Route Handler to api is the cancel case. A drop after the body was sent is CDP `Fetch.enable` with `requestStage: 'Response'` and `Fetch.failRequest`: the body goes over the network and api saves the file, only the response is lost. `page.route` does not fit there: with it Chrome never fires `xhr.upload.onload`.
- View and delete (`e2e/meeting-file-view-delete.spec.ts`). Chromium from Playwright does not play H.264, so the playable video is `e2e/fixtures/clip.webm` (VP9, 60 s, 536 KB, light frames so that Chromium gets the metadata after ~80 KB; it was rendered from canvas frames with the ffmpeg that Playwright downloads, `~/Library/Caches/ms-playwright/ffmpeg-*`). WAV and PNG are generated by `wavBytes` and `pngImage` from `e2e/file-bytes.ts`; MOV is `fileBytes('mov', …)`, a signature plus random bytes, which Chromium cannot decode. Seeking: CDP `Network.emulateNetworkConditions` with `downloadThroughput` 32 KB/s, wait for the metadata and `networkState === NETWORK_IDLE` (with `preload="metadata"` Chrome stops reading), set `currentTime` to the middle, then assert the middle was not buffered and that a request with `Range: bytes=<middle offset>-` got 206. Without the idle wait Chrome sometimes kept reading the open stream and never sent a new Range. Headless Chromium turns a PDF navigation into a download, so the PDF case checks the link (`target="_blank"`) and the headers of the view response instead.
- Reports: `playwright-report/` (HTML, `npx playwright show-report`) and `test-results/` (traces of failed tests); both are in the root `.gitignore` and in the ESLint ignores.
- turbo runs `web#test:e2e` after `api#test:e2e` (see the root `CLAUDE.md`); the Stop hook does not run these tests, the pre-commit hook does.

## Verifying UI changes

A task that touches the look of the interface or the interaction with it (components, pages, styles, `globals.css`, on-screen texts) is done only after the two checks below. `lint`, `check-types` and `build` do not replace them: they do not see layout shifts, weak contrast and lost presses. Until both checks pass, do not call the task done. If a check is impossible (the dev server does not respond, no browser access), say what remains unverified.

- **Visual check through Playwright MCP** (`.mcp.json`). The dev server is already running, do not start it: open the changed screen at `http://localhost:3000` in a real browser, walk through the scenario as a user (clicks, typing, keyboard) and look at the screenshot, not only the DOM snapshot. Check:
  - desktop and a width of ~375 px: no horizontal scroll, nothing sticks out past the margins;
  - every affected state: hover, keyboard focus, error, waiting for a response, empty and filled;
  - the dark theme if colors changed (class `.dark` on `<html>`);
  - the console: no new errors or warnings.
- **Cross-check against the `ui-ux-pro-max` skill.** Invoke the skill and go through its `references/quick-reference.md` by priority: first categories 1–3 (accessibility, touch and interaction, performance), then the others the change touched. Check accessibility with an axe-core run on the affected page too: there must be no new violations. The "Pre-Delivery Checklist" in `references/pro-rules.md` is written for native apps, so take from it what applies to the web (reduced-motion, `aria-hidden` on decorative icons, labels and errors on fields). Fix findings in the changed code and only list findings outside it in the answer. Do not apply a skill recommendation that contradicts the repository rules or the task, and name the discrepancy in the answer.

Test account for manual and browser checks: `demo@example.com` / `video-meetings-demo`, with 5 meetings in the dev database. Use it instead of registering new accounts: sign in through `/login`, or take the token from `POST /auth/login` on api and put it into the `access_token` cookie. Prepare the data a check needs (meetings, files) under this account through the api REST. Never delete it: if the database was wiped (`docker compose down -v`) and login answers "Неверный email или пароль", register it again with the same credentials. A state that needs another user (a foreign meeting or file) is the only reason to create one; delete it after the check (`DELETE FROM users WHERE email = …`, its meetings and file records go with it by cascade, the files on disk under `apps/api/storage/<meetingId>` do not). The e2e tests are different: they create a `user-<uuid>@example.com` per run on purpose and leave it behind.

Do not restart the user's server: if it needs a restart (`globals.css` edits, new packages), remind them in the answer. A running `next dev` does not pick up `globals.css` edits, so check them on a separate production build: `npm run build -w web`, then `npm run start -w web -- -p 3100`, and open `http://localhost:3100`. Build without turbo: its cache stores `.next/**`, including the `.next/dev` of the running server. Afterwards stop only your own process, by PID or by port 3100, not by name: the dev server is also called `next-server`.

Delete the screenshots and logs created by the check when you are done: `.playwright-mcp/` is not in `.gitignore`.

All screenshots save to /screenshot folder

## Code notes

- `cacheComponents` and `partialPrefetching` are enabled in `next.config.ts`. Data is dynamic by default; caching is switched on explicitly with `'use cache'` together with `cacheLife` and `cacheTag`. Accessing uncached data (`fetch`, `cookies()`, `connection()` and so on) outside `<Suspense>` breaks the route prerender. Next shows the ways to fix it in the dev overlay and in the `next build` output. The Edge runtime is not supported.
- On client-side navigation a route is not unmounted but hidden through React `<Activity>`. State is preserved; effects are cleaned up and created again when the route becomes visible again. Keep the camera, microphone and WebRTC connections in effects with cleanup. More: `node_modules/next/dist/docs/01-app/02-guides/preserving-ui-state.md`.
- Tailwind 4 is connected through the Turbopack loader `@tailwindcss/turbopack` (`turbopack.rules` in `next.config.ts`), there is no PostCSS config. The styles live in `src/app/globals.css`. A running `next dev` does not pick up edits to `globals.css` itself (`@theme`, `@utility`, custom rules), although it does pick up new Tailwind classes from `.tsx` files: it must be restarted after such an edit, and how to verify such edits without a restart is described in "Verifying UI changes".
- ESLint is pinned to 9.x: the plugins from `eslint-config-next` 16.4 (react, jsx-a11y, import) do not support ESLint 10. Raise the version only together with `eslint-config-next`.
- A page title is set as `title: 'Page title'`: the template `%s — Video meetings` lives in the metadata of the root `layout.tsx`, and the home page uses `default`.
- `layout.tsx` sets `suppressHydrationWarning` on `<html>` and `<body>`: browser extensions add attributes to them before hydration (for example, `trancy-version`), and without it the dev overlay showed "1 Issue" with a hydration error on every page. The attribute applies only to the element itself, not to nested ones.
- Open the dev server via `localhost`. For `127.0.0.1` and any IP, Next blocks the HMR socket (the line `Blocked cross-origin request to Next.js dev resource /_next/hmr` in `.next/dev/logs/next-development.log`), and the page does not hydrate: the "eye" button does not toggle, the form goes out as a plain POST and comes back with red fields. Another host is allowed by `allowedDevOrigins` in `next.config.ts`.

## Calling the api and auth

The browser never calls api directly: requests come from the web server (Server Actions, Server Components, Route Handlers), so CORS is not enabled in api.

- `src/lib/api.ts`: `apiFetch(path, init)` is a `fetch` to api with a 10 s timeout, `readJson(response)` is the response body as an object (empty if it is not JSON). The api address comes from the server-side variable `API_URL`, by default `http://localhost:4000`. Next reads `.env*` from `apps/web`, not from the repository root: set it in `apps/web/.env.local` or in the environment (it is passed through turbo in `globalPassThroughEnv`).
- `src/lib/session.ts`: `createSession(accessToken)` puts the JWT from api into the cookie `access_token` (httpOnly, `SameSite=Lax`, `Secure` in production, the lifetime is taken from the token's `exp`), `deleteSession()` removes it, `getSession()` returns `{ email }` or `null`, `getAccessToken()` returns the raw cookie value, `getApiToken()` returns it only when `readSession` accepts it (otherwise `null`; the file Route Handlers use it to check the session themselves). Call protected api routes with `authHeader(token)` from `src/lib/api.ts` (`Authorization: Bearer <jwt>`), as `getMeetings()` does; the token stays on the server, do not pass it to client components. The token parsing lives in `src/lib/access-token.ts` without `next/headers`, so that proxy can use it too.
- `getSession()` and proxy check the session optimistically, by the cookie only: the token must be parseable, contain `email` and not be expired. web does not verify the signature (the JWT secret is needed only by api), api does it on every request, so these checks are not suitable for data access: they only choose what to show. If the cookie is left over from a deleted user (for example, after `docker compose down -v`), the interface considers them logged in: the home page shows their email and an empty meeting list until they press "Выйти". A token with a wrong signature (for example, after changing `JWT_SECRET`) also passes these checks, and api answers 401: instead of the list the home page shows a load error with the buttons "Повторить" and "Выйти". `getSession()` calls `connection()` before checking the expiry: with `partialPrefetching` the code after `cookies()` runs already during the shell prerender, where `Date.now()` is forbidden, and without it the home page with a session failed in dev with the error `unstable value Date.now()`.
- `src/proxy.ts` (in Next 16 this is the former middleware): before rendering it redirects GET `/` and the matched paths under `/meetings/` without a session cookie to `/login`, and GET `/register` and `/login` with a cookie to `/`. A form's Server Action arrives at the same path as a POST request, so proxy lets everything except GET through. The `matcher` value must stay a constant: `/`, `/meetings/:id`, `/meetings/:id/((?!files(?:/|$)).*)`, `/register`, `/login`. Account for a new page both in `matcher` and in the function itself: right now `/` and the matched `/meetings/…` paths require a session, and the other paths from `matcher` do not allow one. Nested pages under a meeting are closed too, except the `/meetings/<id>/files` subtree: it holds the file Route Handlers and must stay out of `matcher`, because for every matched request Next clones the body for proxy and cuts it at 10 MiB before the function even runs, so an upload would arrive truncated. Those Route Handlers check the session themselves. `e2e/meeting-files.spec.ts` ("без входа") fails if the download handler loses its redirect, which proves the subtree is outside proxy.
- The home page `/` (`src/app/page.tsx`) is closed: without a session proxy sends the user to `/login`. The static shell contains the header (`AppHeader` from `src/components/app-header.tsx`, shared with the meeting page) with the logo, the heading "Ваши встречи" and the button "Создать встречу" (no action yet: creating meetings is not implemented in web). Everything that reads the cookie or calls api is moved into separate `<Suspense>` boundaries (with `cacheComponents` such a read outside one breaks the build) and streams after the shell: `Account` inside `AppHeader` (the email and the button "Выйти") and `MeetingsSection` (the meeting list, `meetings-skeleton.tsx` while loading). There are two boundaries so that the header does not wait for a slow api. If `Account` finds no session (a rare race with proxy, for example the token expired between them), it calls `redirect('/login')`. Logging out is the Server Action `logout` from `src/app/actions.ts`: it removes the cookie and calls `redirect('/login')`; a redirect to `/` would cause an extra hop through proxy.
- Meetings on the home page. `getMeetings()` from `src/lib/meetings.ts` calls `GET /meetings` with the token from the cookie and returns a list or `null`: there is no token, api answered with a non-2xx, the response is not a list, or api is unreachable (the reason is written to the server log). `null` is rendered as an `Alert` "Не удалось загрузить встречи" with the button "Повторить" (`router.refresh()` in `retry-button.tsx`), and the header with "Выйти" stays in place. The `Meeting` type mirrors `MeetingView` from api (the date arrives as an ISO string): when you change one, change the other. "Последние встречи" shows the three meetings with the latest date (`LATEST_MEETINGS_COUNT`, newest first), "Все встречи" shows the whole list in the same order. The blocks are shown when there is at least one meeting, so with three or fewer they duplicate each other. Data is not cached, every visit goes to api. There is no pagination: api returns all meetings at once.
- A card in "Последние встречи" and a row in "Все встречи" open the meeting page. The link is the title itself (`MeetingLink`), and its `::after` (`after:absolute after:inset-0`) stretches the click area over the whole `relative` card or row, so the link's accessible name is the title only, not the date and participant count. The link has no outline of its own: the card or row draws the focus ring through `has-[a:focus-visible]` with `outline-focus`. The list `ul` and the rows inherit the card's radius (`rounded-[inherit]`, `first:`/`last:`) so that the ring on the first and last row follows the card's corners.
- The meeting page `/meetings/[id]` (`src/app/meetings/[id]/page.tsx`): `AppHeader`, the link "Все встречи" back to `/`, then in `<Suspense>` (`params` is awaited inside it, as the Cache Components docs require for a route without `generateStaticParams`) the title as `h1`, the date through `MeetingDate` and the "Участники" block: a list of the strings from `participants` or "Участников нет". `getMeeting(id)` from `src/lib/meetings.ts` calls `GET /meetings/:id` and returns the meeting, `MeetingLookup.NotFound` (an enum exported next to it; api answered 404: the meeting is someone else's or does not exist, api does not distinguish them, and web must not either) or `null` (no token, another non-2xx, api unreachable). `MeetingLookup.NotFound` renders "Встреча не найдена" as the page's `h1`, `null` renders the `Alert` "Не удалось загрузить встречу" with "Повторить". The response is streamed, so a missing meeting answers 200, not 404. `getMeeting` is wrapped in React `cache()`: `generateMetadata` calls it too (the tab title is the meeting title or "Встреча не найдена"), and within one request api is called once.
- The "Файлы" block on the meeting page (`src/app/meetings/[id]/meeting-files.tsx`) sits in its own `<Suspense>` after "Участники" and shows the files in api order (newest first): name, size and upload date (through `MeetingDate`), and the actions "Смотреть" (only for viewable formats), "Скачать" and "Удалить". Below `sm` the row hides its decorative file icon and the actions are icon-only 44×44 targets with `aria-label` "<action> <name>", so the name keeps room on a 375 px screen. The row skeleton in `MeetingFilesPlaceholder` mirrors a row with all three actions (110 px, 100 px and a round one from `sm`, three 44 px circles below it). States: "Файлов пока нет", `MeetingFilesSkeleton` while loading (`MeetingSkeleton` of the whole page includes the same placeholder) and the `Alert` "Не удалось загрузить файлы" with "Повторить". `getMeetingFiles(id)` from `src/lib/meeting-files.ts` calls `GET /meetings/:id/files` and returns a list or `null` (any failure, including 404: the block is rendered only after the meeting itself was found). It is wrapped in `cache()`, and `MeetingDetails` calls it without `await` before `getMeeting`, so both requests to api run in parallel. The `MeetingFile` type mirrors `MeetingFileView` from api (`createdAt` arrives as an ISO string): when you change one, change the other. `formatFileSize` (`src/lib/file-size.ts`, separate from `meeting-files.ts` because the client upload component uses it too and `meeting-files.ts` imports `next/headers`) uses binary units with fixed Russian labels (`Б`, `КБ`, `МБ`, `ГБ`, 1 ГБ = 1 GiB as in the PRD limit), not `Intl` units: ICU writes the kilobyte as `кБ`.
- Download, `src/app/meetings/[id]/files/[fileId]/route.ts`. "Скачать" is a plain `<a href>` styled with HeroUI `buttonVariants`, not `next/link`: the browser writes the file to disk itself, without JS and tab memory. The Route Handler and the view one below are thin wrappers over `proxyFile(request, apiPath, failureText)` from `src/lib/file-proxy.ts` (with `filePath(meetingId, fileId)`, which the file rows and the delete action use too). It takes the token from `getApiToken()` (no valid session → `redirect('/login')`), calls `GET /meetings/:id/files/:fileId` with `fetch` and `request.signal`, forwards `Range` and `If-Range`, and returns `upstream.body` as a stream with a whitelist of response headers (`Content-Type`, `Content-Length`, `Content-Range`, `Accept-Ranges`, `Content-Disposition`, `ETag`, `Last-Modified`, `Cache-Control`, `X-Content-Type-Options`). So the file type and name are whatever api sends: change them in api. Not `apiFetch`: its 10 s `AbortSignal.timeout` would cut the body of a long download too. A 404 from api (a foreign or nonexistent file or meeting, api does not distinguish them) becomes the plain text "Файл не найден" with 404: a Route Handler cannot render `not-found.tsx`. Other api errors are passed with their status and the text "Не удалось скачать файл" ("Не удалось открыть файл" for the view), an unreachable api gives 502. Measured on a production build: a 1 GiB file downloads with the same SHA-256 and the web process grows by ~106 MB; `Range` gives 206 with the right `Content-Range`.
- View, `src/app/meetings/[id]/files/[fileId]/view/route.ts` → api `GET /meetings/:id/files/:fileId/view` (`inline`, the type from api's format table, `nosniff`), through the same `proxyFile`, so `Range` reaches api and the 206 comes back as a stream: a `<video>` seeks to any point without loading the file first. Which files get "Смотреть" is decided by `viewKindOf(mimeType)` from `src/lib/file-rules.ts` (`video/*`, `audio/*`, `image/*`, `application/pdf`); it mirrors `isViewable` of api: change both together. PDF is a plain `<a target="_blank" rel="noopener">` to the view URL: the browser's own viewer in a new tab works with every page of the document, while an `<iframe>` on iOS shows only the first page. Video, audio and images open in a HeroUI `Modal` (`file-viewer.tsx`, client, `size="lg"`, `sm:max-w-3xl` except audio) with the file name as the heading: `<video controls preload="metadata" playsInline>`, `<audio controls preload="metadata">` or `next/image` with `unoptimized` and `width`/`height` 0 (the size is unknown; CSS limits it to `70dvh`). The media element is rendered only while the modal is open, so closing it stops playback and drops the connection. `onError` of the element (format or codec not supported, for example MOV with H.264 in Chromium) replaces it with an `Alert` "Браузер не может открыть этот файл" and a "Скачать" link; `canPlayType` is not used, because Chrome reports `video/quicktime` as unsupported and still plays many MOV files.
- Delete, `src/app/meetings/[id]/delete-file-button.tsx` (client) and the Server Action `deleteMeetingFile(meetingId, fileId)` in `src/app/meetings/[id]/actions.ts`. The trash button opens a HeroUI `AlertDialog` ("Удалить файл?" with the name, "Отмена" and "Удалить"); the action calls api `DELETE` through `apiFetch` and then `refresh()` from `next/cache`, so the row disappears in the same transition. A 404 counts as success (the file is already gone). No valid session in the cookie or a 401 from api (for example, a token with a wrong signature, which web's optimistic check accepts) removes the cookie and calls `redirect('/login')`: without `deleteSession()` proxy would send `/login` with a parseable cookie straight back to `/`. Other failures come back as `{ error }` and are shown inside the dialog (`role="alert"`, `text-danger-soft-foreground`); while the request runs "Удалить" is `isPending`, "Отмена" is disabled and the dialog ignores close requests. The trigger leaves the DOM with its row, so after a successful delete the component's unmount effect moves focus to the "Файлы" heading (`tabIndex={-1}`), otherwise it would fall to `body`. HeroUI's dark `--danger` gives 4.34:1 under white text, so the confirm button overrides `--button-bg` and `--button-bg-hover` under `dark:` locally.
- Upload area, `src/app/meetings/[id]/file-upload.tsx` (client). `MeetingFiles` renders it whenever the list loaded, including a meeting without files, and passes the server list (or "Файлов пока нет") as `children` plus `fileIds`. The area is `DropZone` with `FileTrigger` and a HeroUI `Button` "Выбрать файлы" (`allowsMultiple`, `size="lg"` for a 44 px target on phones); from a drop only `kind === 'file'` items are taken, directories are ignored for now. Every file is a separate `XMLHttpRequest` (`fetch` has no upload progress) to `POST /meetings/<id>/files` of web with the raw `File` as the body, `Content-Type: application/octet-stream` and `X-File-Name` as `encodeURIComponent` of the name: the same contract as api. At most 3 run at once (`MAX_PARALLEL_UPLOADS`), the rest wait as "В очереди": Chrome keeps 6 HTTP/1.1 connections per origin, and six uploads would block `router.refresh()`, navigation and Server Actions. The XHR starts from the select or drop handler, not from an effect: an effect cleanup would abort it when `<Activity>` hides the route. Each file shows a `ProgressBar` (`aria-label` "Загрузка <name>", the percent from `xhr.upload.onprogress`), then "Сохраняем…" between the end of sending and the 201 (api still renames the file and writes the record), or the error reason. A failed file does not stop the others. On 201 the component calls `router.refresh()` in a transition (the skeleton does not come back) and hides its own row once the server list contains the returned `id`, so the new file appears at the top of the list without a page reload. Results (done, error with its reason, cancelled, rejected) are announced through one `aria-live="polite"` line, not on every percent.
- Upload checks, cancel and retry (same component). Before sending, `rejectionOf(file)` from `src/lib/file-rules.ts` rejects an empty file ("Файл пустой"), one larger than 1 GiB ("Файл больше 1 ГБ") and an extension outside the PRD list ("Формат не поддерживается"), in api's order; the extension is taken from the NFC-normalized, trimmed name, as api does (`parseFileName`), so "Заметки.txt " passes; such a file gets a row with the reason and no request, the rest of the selection uploads. These rules mirror `file-formats.ts` and `MAX_FILE_SIZE` of api (`FILE_FORMATS` plus `.jpeg`, case-insensitive): change both together. The signature of the first bytes is checked only by api; its refusals and other failures become a reason through `uploadErrorOf(status, message)` from the same file (415 "Содержимое не соответствует формату" by api's `message`, 401, 404, 413, 502, a network error as "Связь прервалась", anything else "Не удалось загрузить"). A queued or uploading row has "Отменить" (`aria-label` "Отменить загрузку <name>"): a queued file leaves the queue, an uploading one gets `xhr.abort()`, the browser drops the connection, the upload Route Handler aborts the request to api through `request.signal`, and api removes its `.part` (measured: within 0.2 s, no record). There is no cancel while "Сохраняем…": the body is already sent, and api may still create the file. For the same reason a network error after `xhr.upload.onload` is not an ordinary error: the row says "Связь прервалась после отправки, файл мог сохраниться", has no "Повторить" (a retry would create a duplicate) and the component calls `router.refresh()`, so a file api did save shows up in the list. A failed or cancelled row has "Повторить" in the same place (the same `Button` element, so keyboard focus stays on it) that puts the same `File` back into the queue; a rejected row has no action. The reason text is `text-danger-soft-foreground`, not `text-danger`: HeroUI's dark `--danger` on a card is below 4.5:1. Finished rows stay until a reload, there is no "dismiss" yet. The drop area lists the formats and the limit (`FILE_FORMATS`).
- Upload Route Handler, `src/app/meetings/[id]/files/route.ts` (`POST` only). It is outside proxy `matcher` for the same reason as the download one: proxy would clone the body and cut it at 10 MiB. Not a Server Action either (1 MB limit, body kept in memory). It checks the session itself through `getApiToken()` (no valid cookie → JSON 401, the client is an XHR, a redirect is useless), rejects a foreign `Origin` with 403 (Server Actions get this check from Next; `SameSite=Lax` already keeps the cookie off cross-site POSTs, this is defense in depth) and a request without `Content-Length` with 411. The e2e test of the handler sends the 411 case through raw `node:http` with `Transfer-Encoding: chunked`: Playwright's `request` always sets `Content-Length` itself. The body is piped to api with `node:http` (`node:https` for an `https` `API_URL`) and `pipeline(Readable.fromWeb(request.body), …)`, with the JWT, `Content-Length` and `X-File-Name` forwarded and `Content-Type` always set to `application/octet-stream`, whatever the browser sent; api's status, JSON body, `Content-Type` and `Location` come back as is, an unreachable api gives 502. Not `fetch`: undici copies every chunk, and the research measured RSS growing by about the file size on 1 GiB. `request.signal` aborts the request to api when the browser drops the connection. `Content-Length` is forwarded so that a body cut on the way reaches api as an abort, not as a short file. Measured on a production build: 1 GiB uploads in ~2 s on localhost with web RSS +115 MB and the same SHA-256 after download. Node closes a request whose body takes longer than `requestTimeout` (300 s), and `next start` does not change it: see README, "Файлы встреч".
- Meeting date and time. `MeetingDate` (`meeting-date.tsx`) shows them in the browser's time zone: a server component would format the time in the server's zone, and a user in another zone would see someone else's time. The component is a client one, built on `useSyncExternalStore`: the server and hydration render UTC with the label "UTC" (identically in both places, so there is no hydration error, and without JS the time is at least correct), and after hydration React substitutes the local time.
- HeroUI skeletons shimmer even with `prefers-reduced-motion`. The skeleton wrappers in `src/components/app-header.tsx`, `meetings-skeleton.tsx`, `src/app/meetings/[id]/page.tsx` and `meeting-files.tsx` carry the class `motion-reduce:[&_.skeleton::after]:animate-none`: a new skeleton needs the same. Make the height of a button skeleton equal to the button's: it depends on the screen width (`lg`: 44 px up to 768 px and 40 px wider, `md`: 40 and 36, `sm`: 36 and 32), otherwise the header jumps on load.
- Registration, `/register` (`src/app/register`): the client form `register-form.tsx` calls the Server Action `register` from `actions.ts`. It validates the fields, sends `POST /auth/register`, sets the cookie and calls `redirect('/')`. A 409 response becomes an error under the email field, 400 becomes field errors, and api unavailability or a timeout becomes a general `Alert`. The rules in `validation.ts` mirror `RegisterDto` in api: when you change one, change the other.
- Login, `/login` (`src/app/login`): built like registration. The form `login-form.tsx` calls the Server Action `login` from `actions.ts`: it validates the fields, sends `POST /auth/login`, sets the cookie and calls `redirect('/')`. The statuses 401 and 400 become one general error "Неверный email или пароль" in an `Alert`: api does not distinguish "no such user" from "wrong password", and web must not either. api unavailability or a timeout is a different general error. The password at login is checked only for being non-empty (`login/validation.ts`): the length rules belong to registration. `validateEmail` is shared, it comes from `register/validation.ts`. The fields have `autoComplete="username"` and `current-password` so that password managers work. The form was copied from the registration one together with the behavior described in the following items: when you change one, change the other. `BrandPanel` is shared and lives in `src/components`.
- The pages `/register` and `/login` link to each other with a line under the card ("Уже есть аккаунт? Войти", "Нет аккаунта? Зарегистрироваться"); the link is styled with the classes `link text-accent underline`. The top padding of the `<section>` in both pages (`pt-[max(…)]`) is computed from the height of the block so that the form stays centered and does not jump on errors. If you changed the block height (a new line, different text), measure the wrapper's `offsetHeight` and recompute the constants in both: on a phone the height plus ~3.5rem of reserve for the general error, on a wide screen (the logo is hidden) the height minus ~0.25rem.
- Form submission (registration and login): `<Form action={formAction} onSubmit={handleSubmit}>`. In a browser with JS `onSubmit` fires: it calls `preventDefault()` and `startTransition(() => formAction(formData))`. After `preventDefault()` React does not run `action` and does not reset the fields, so what the user typed does not disappear on every server error. `action` is needed for a submit before hydration or without JS: the form goes out as a plain POST (Next adds the hidden `$ACTION_*` fields), registration works end to end, and the password does not end up in the URL. Without `action` and `method` the browser would send a GET, and the password would land in the address `/register?email=…&password=…`.
- Field errors live in the form state (`errors`), not in HeroUI's `validate` and `validationErrors`; `Form` has `validationBehavior="aria"`. The reason: the built-in validation updates the error only when the field loses focus, and a corrected field stayed red. An error appears when leaving a field that was typed into, or on submit; while it is shown, it is recomputed on every input and disappears as soon as the value becomes valid, and a new error does not flash while typing. A server response replaces the errors on screen, and the first edit of a field clears its server error. The general-error `Alert` is recreated on every response (`key`) so that a screen reader announces a repeated error too.
- The form buttons (the password "eye" and submit) are pressed with `preventFocusOnPress`: a mouse press does not move focus out of the field. Otherwise blur shows an error under the email, the block below shifts by ~20 px, the button moves from under the cursor, and the browser does not deliver `click` to it. In this version of React Aria `onPress` fires exactly from `click`, so the "eye" did not toggle the password and a click on the upper half of "Создать аккаунт" was lost. Add a new button inside a form with blur validation the same way. From the keyboard the buttons work as usual.
- If a Server Action ends with `redirect()`, Next rejects its promise on the client and remounts the subtree. So a form hidden through `<Activity>` keeps neither the password nor old errors, and there is no need to reset it manually.

## HeroUI

HeroUI v3 (`@heroui/react`, `@heroui/styles`) is installed in web. The styles are connected in `src/app/globals.css` with the line `@import '@heroui/styles'` right after `@import 'tailwindcss'`. No Provider is needed. Use the `heroui-react` skill before working with HeroUI: the v3 API is incompatible with v2, components are compound (`Card.Header`), the handler is called `onPress`. The installation steps in the skill assume PostCSS, but here Tailwind is connected through `@tailwindcss/turbopack`, so `postcss.config.mjs` is not needed. HeroUI defines the CSS variables `--background` and `--foreground`, do not override them in `globals.css`. After installing new packages `next dev` must be restarted, otherwise the styles are not picked up.

- Compound components (`Card.Header`, `Alert.Title`) work in Server Components too.
- HeroUI v3 has no file components. `DropZone` and `FileTrigger` come from `react-aria-components`, the library HeroUI is built on: it is a direct dependency of web (`^1.22.1`, the version HeroUI resolves), imported by subpath (`react-aria-components/DropZone`) and only in client components (the package is `client-only`). Without an `aria-label` `DropZone` names its hidden keyboard button with the English "DropZone", so give it a Russian one. Its state comes as attributes (`data-drop-target`, `data-focus-visible`): style them with `data-[…]:` classes.
- Tailwind 4 `outline-none` sets `--tw-outline-style: none`, so a later `outline-2` draws nothing: do not combine them on one element, the repository's focus rings are `outline-2 outline-focus` without `outline-none`. `--field-border` is transparent in the dark theme, so it is not usable for a border that must stay visible there (the upload area uses `border-muted/50`).
- Icons come from `@gravity-ui/icons`, as in the HeroUI docs. Import them one by one: `import Eye from '@gravity-ui/icons/Eye'`, not from the package root. The root barrel is not in Next's `optimizePackageImports` and pulls all ~800 icons into the dev bundle (measured: +1.5 MB of JS on a page). Icons do not hide themselves from screen readers, add `aria-hidden="true"` to decorative ones.
- The base HeroUI styles set neither a background nor a text color on `body`. A page that needs the theme sets `bg-background text-foreground` itself (example: `src/app/register/page.tsx`). The dark theme is switched on only by the class `.dark` or `data-theme="dark"`, it does not switch on by itself from `prefers-color-scheme`.
- When leaving a page with a form and returning to it, React Aria writes "If you do not provide a visible label…" to the dev console: `<Activity>` detaches the labels' ref. The labels are in place after returning; the production build has no such warning.
- Contrast. The default HeroUI colors do not pass WCAG AA (`--danger` and `--accent` give 3.6:1, `--muted` 4.1–4.8:1), and fields have no border. `globals.css` overrides `--accent`, `--danger`, `--muted`, `--field-border` and `--field-border-width` for the light theme: the selector `:root:not(.dark, [data-theme='dark'])` keeps the values out of the dark one. The rule sits outside any layer, and HeroUI declares the variables in `@layer base`, so it wins at any specificity. After editing the tokens run axe-core: `color-contrast` on `/register`, `/login` and `/` must not fire, either in the normal state or with errors.
- `InputGroup`: put `min-w-0` on `InputGroup.Input`. An `input` has `min-width: auto` and `size=20` (≈197 px) by default, so the "icon, field, button" group does not shrink and on screens as narrow as ~370 px the button sticks out past the field. While `--field-border-width` is greater than zero, HeroUI draws separators on `InputGroup.Prefix` and `InputGroup.Suffix`: remove them with the class `border-0`. HeroUI draws the required-field asterisk through `::after` on `Label`, and it ends up in the field's accessible name ("Email*"): if all fields are required, remove it with the class `after:content-none`.
