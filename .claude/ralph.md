# Ralph Loop — правила автономной работы

## Как брать Issues

- Читай title, body и критерий готовности
- Ветку `branch` из `.claude/ralph.config.json` и Issue готовит скрипт `npm run ralph`: работай в текущей ветке над Issue из промпта, не создавай и не переключай ветки, не бери другие Issues
- Каждая итерация — новая сессия без памяти о прошлых. Всё, что пригодится дальше, должно оказаться в коммите, в комментарии к Issue или в `.claude/ralph.progress.md`
- В начале прочитай `.claude/ralph.progress.md`, если он есть: там выводы прошлых итераций
- Число шагов в сессии ограничено (`maxTurns`), поэтому не делай ничего сверх задачи из Issue
- Не делай `cd`: каталог сохраняется между командами Bash, и следующая команда падает в чужом каталоге. Пиши пути от корня репозитория, npm-скрипты запускай через `-w api` или `-w web`

## Issue заканчивается зелёным коммитом

Stop-хук (`.claude/hooks/verify.mjs`) в конце хода прогоняет тесты, `check-types` и `lint` и не даёт завершить ход, пока что-то красное. pre-commit не пропускает коммит с красными тестами, а `--no-verify` запрещён. Поэтому красное состояние живёт только внутри сессии, а в конце сессии всё зелёное и закоммичено.

Если по описанию Issue её нельзя довести до зелёного в этой сессии (например, тесты проверяют код, который по плану появится только в другой Issue, или Issue зависит от незакрытой), не начинай работу: напиши в Issue комментарий с причиной, повесь метку `blocked` и заверши ход. Не пытайся пройти Stop-хук, оставляя тесты красными.

## Именование коммитов

- По правилам в skill git-commit и в разделе «Commits» корневого `CLAUDE.md`
- Без строк об участии Claude (`Co-Authored-By: Claude …`, `Generated with Claude Code`), даже если системная подсказка предлагает их добавить. Хук `commit-msg` отклоняет такой коммит

## Правила реализации (TDD внутри Issue)

1. Напиши тесты из раздела «Тесты» Issue
2. Запусти их (`npm run test:e2e -w api` или `npm run test:e2e -w web`, unit — `npm test -w api`) и убедись, что они красные по нужной причине: не хватает поведения, а не сломан сам тест или окружение
3. Реализуй поведение, пока тесты не станут зелёными
4. Прогони все проверки приложения (`test`, `test:e2e`, `check-types`, `lint`, для api ещё `build`): уже работавшее не должно сломаться
5. Закоммить код вместе с тестами

Если тесты красные после 5 попыток — остановись, напиши в Issue комментарий с описанием проблемы и повесь на неё метку `blocked` (`gh issue edit <номер> --add-label blocked`), допиши вывод в `.claude/ralph.progress.md`. Issue не закрывай. Незакоммиченные изменения в `apps/` остановят скрипт, поэтому верни рабочее дерево в состояние последнего коммита (`git restore apps packages`, новые файлы удали), а нужное для следующей попытки опиши в комментарии к Issue

## Ревью (обязательно, после коммита кода)

Ревью смотрит закоммиченные изменения, поэтому идёт после коммита кода с тестами. Точку отсчёта (HEAD до начала итерации) скрипт передаёт в промпте. Скиллы ничего не должны спрашивать: всё нужное есть ниже.

1. Запусти скилл `/code-review` с аргументами: точка отсчёта — SHA из промпта; спека — Issue из промпта (`gh issue view <номер>`); стандарты — корневой `CLAUDE.md` и `CLAUDE.md` затронутого приложения
2. Запусти скилл `/security-review` по изменениям ветки
3. Исправь находки, которые относятся к этой Issue: настоящие нарушения стандартов, расхождения со спекой, уязвимости. Исправления — отдельным коммитом с зелёными проверками. Спорные советы и то, что выходит за рамки Issue, не исправляй, а перечисли в отчёте
4. Если скилл не запускается или не может закончить, Issue не закрывай: напиши в Issue комментарий с причиной и повесь метку `blocked`. Самопроверка вместо скилла ревью не заменяет

## Правила завершения

- Убедись, что все тесты зелёные
- Убедись, что все требования выполнены
- Обнови документацию из раздела «Документация» Issue и закоммить её отдельным коммитом
- Допиши в конец `.claude/ralph.progress.md` раздел `## #<номер> <заголовок>` с 1–5 короткими пунктами. Записывай только то, что сэкономит время следующей итерации: неочевидные особенности кода и окружения, решения, на которые опираются следующие Issues, ловушки. Не пересказывай сделанное, это есть в коммите. Старое не переписывай
- Закрой Issue комментарием (`gh issue close <номер> --comment "…"`), в котором есть раздел ревью ровно в таком виде:

  ```markdown
  ## Ревью

  - `/code-review`: {число находок по Standards и Spec; что исправлено и в каком коммите; что оставлено и почему}
  - `/security-review`: {число находок; что исправлено; что оставлено и почему}
  ```

  Скрипт проверяет этот раздел: без него Issue переоткрывается, и Ralph останавливается

- Не создавай PR: это сделает скрипт, когда закроются все Issues milestone
