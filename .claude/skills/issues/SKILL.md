# Plan Generator

Прочитай план из файла: $ARGUMENTS

Для каждой фазы создай milestone и issues в github, используя gh CLI.

## Порядок действий

1. Прочитай файл плана
2. Проверь каждую задачу по правилам из раздела «Проверка задач». Если задача им не отвечает, не создавай Issues: назови задачи и причину и предложи исправить план
3. Для каждой фазы создай milestone:
   `gh api repos/:owner/:repo/milestones -f title="Фаза N: название"`
4. Для каждой задачи в фазе создай Issue в порядке плана: Ralph loop берёт Issues по возрастанию номера
   `gh issue create --title "..." --body "..." --label "..." --milestone "..." --project "video-meetings"`

## Проверка задач

Каждая Issue решается Ralph loop за одну сессию и заканчивается зелёным коммитом: Stop-хук и pre-commit не пропускают красные тесты. Поэтому задача:

- описывает наблюдаемое поведение, а не шаг процесса или слой кода («сначала тесты», «поле в модели», «документация» — не задачи);
- содержит свои тесты, которые станут зелёными в этой же Issue;
- опирается только на задачи выше себя.

## Формат Issue

**Title:** поведение из задачи плана, коротко (без `- [ ]`)

**Labels:** по полю «Затрагивает» фазы (`backend`, `frontend`, `database`), плюс `documentation`, если задача меняет документацию

**Body:**

```markdown
## Поведение

{что начинает работать, 1–3 предложения}

## Тесты (пишутся первыми)

- [ ] {сценарий: действие → ожидаемый результат}
- [ ] ...

Где: {apps/api/test/<файл>.e2e-spec.ts или apps/web/e2e/<файл>.spec.ts}

## Реализация

- {что меняется в коде}

## Документация

- {какие файлы обновить и что в них описать}

## Готово, когда

- тесты из списка зелёные, остальные тесты не сломаны;
- `check-types`, `lint` (и `build` для api) зелёные;
- код и документация закоммичены.

## Зависит от

{#номер Issue или «—»}

---

Фаза N «{название}». Цель: {цель фазы}.
План: `docs/plan-….md`, PRD: `docs/prd-….md`.
```
