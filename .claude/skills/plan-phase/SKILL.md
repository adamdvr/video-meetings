# Plan generator

Прочитай PRD из файла: $ARGUMENTS

Создай план реализации и сохрани в файле 'docs/plan-$ARGUMENTS.md' (используй перевод на английский и kebab-case)

## Структура плана

```markdown
# Plan: {название фичи}

**PRD:** $ARGUMENTS

**Дата:** {текущая дата}

## Фазы реализации

## Фаза 1: {название}

**Цель:** {что дает эта фаза}

**Затрагивает:** {backend / frontend / database}

**Задачи:**

- [ ] **{Наблюдаемое поведение}.** Тесты: {сценарии, которые пишутся первыми}. Код: {что меняется}. Документация: {какие файлы}.
- [ ] **{Следующее поведение}.** Тесты: … Код: … Документация: …

**Когда готова:** Конкретный критерий

## Фаза 2: {название}

...
```

## Правила разбивки на фазы

- Каждая фаза должна давать рабочий результат.
- Фазы независимы, можно остановиться после любой.
- Первая фаза как минимальный рабочий путь (Tracer bullet).
- Не больше 5 задач в одной фазе.
- Backend и frontend одной фичи разные фазы.

## Правила разбивки на задачи

Задача — это вертикальный срез: одно наблюдаемое поведение, которое за одну сессию проходит путь «тесты красные → реализация → тесты зелёные → коммит». Из каждой задачи получится Issue для Ralph loop, а там Stop-хук и pre-commit не дают закончить ход и закоммитить, пока тесты красные.

- Тесты — часть задачи, а не отдельная задача. Задача «сначала написать тесты» не может завершиться зелёной: её тесты проверяют код из следующих задач.
- Задача не бывает слоем без наблюдаемого поведения («поле в модели и миграция», «сообщения модуля»). Слой входит в первую задачу, которой он нужен.
- Документация — часть задачи, которая меняет описанное поведение, а не отдельная задача.
- Каждая задача после выполнения оставляет все тесты зелёными и не ломает уже работающее.
- Задача опирается только на задачи выше себя: Ralph берёт Issues по возрастанию номера.
- Тесты задачи описаны сценариями: что делает пользователь или клиент api и что получает. Ожидаемый отказ (400, 401, 404) проверяется вместе с позитивным сценарием, иначе тест «пройдёт» на 404 от ещё не существующего роута.
- Задача по объёму укладывается в одну сессию агента. Если сценариев больше десятка или затронуто больше трёх модулей, раздели её по поведению.

## Правила

- Читай PRD внимательно, план должен покрывать все критерии готовности.
- Не добавляй задачи, которых нет в PRD.
- Если PRD не полный, задай вопрос перед созданием плана.
